01

The Governing Principle

One idea drives every sequencing choice below.

If the systems don't work in simulation mode, they won't work after we've spent a ton of time polishing the turds.

This game's fun lives in its systems — the roster market, the economy, growth, Discipline mispricing, job interconnection, the whole Johnson loop. Those are data, menus, and math: they can be built and proven fun in text, where iteration is instant and free. The tactical missions are content those systems generate; their eventual visuals are a rendering layer, not the game. So we build the entire game as a text/simulation first — a real, complete, playable thing — and only skin it with visuals once the core has earned it. Simulation mode is a lie detector: it tells us cheaply whether the loop is fun before a single sprite is drawn.

Why this game specifically suits it: we built the whole design as data per "systems are expensive, rows are cheap." A site's obstacles are affordance lists; skills gate them; the job grammar generates objectives. That means the design came out text-ready by accident — a text renderer just reads the data the generators already produce and prints choices. Nothing needs re-designing to run in simulation mode.

The Fidelity Ladder

Three renderings of the same underlying systems. We build the whole game at the middle rung first.

Quick-resolve

One aggregate roll, instant. The skip button, and the always-available fallback that keeps the game playable while anything else is half-built.

exists from Phase 1

Scene-text

Describe the scene from the site data, offer the affordance skill-rolls, resolve the chosen one, mark the result, advance. Interactive, choice-driven, no rendering. Every system, no skin.

← we build here first

Full spatial

Top-down positioning, radius movement, cover geometry, the visual pillars. The eventual layer, laid over the proven text core, added per pillar.

Phase 3+
What scene-text validates vs. defers. It fully proves the systems, the economy, the roster loop, and job interconnection — the core. It abstracts the spatial tactical feel (exact positioning, cover angles, the radius dance) into scene choices; that specific feel is precisely what the visual layer restores. Since this game's fun lives in the systems, that's the right thing to defer — named, not glossed.
Read that rung carefully — geometry is the ONLY thing it defers. Initiative, the action economy, combat resolution, health tracks and Drain all belong at scene-text, not at the visual layer. Reading this ladder as "scene-text means one roll per obstacle" is what stalled Phase 2 once already; see the Phase 2 work plan, §0.

05

Phase 0 — The First Concrete Tasks

Where we actually started. Pure data design, no gameplay, no art — the bedrock everything instantiates. Complete.

  1. Repo scaffold. New Arcaegium subfolder, index.html, a module structure, git. Match the existing project conventions.
  2. Seeded RNG. A deterministic PRNG utility — the core of the save-as-seeds model, so any generated entity reproduces exactly from its seed.
  3. Runner model + generator. The record schema (attributes, skills, Discipline label + hidden true-archetype, Essence, wounds, Karma, market state). Generation from seed: archetype → spread template → skills → Discipline label at 80/10/10. The derived price function (Discipline lens × skills).
  4. Site model + generator. The schema (three security axes, room/obstacle graph, obstacles as affordance lists, population) and generation from seed, with the three invariants (brute force always available, ≥1 alternate solution chain, no obstacle single-skill-locked).
  5. Day clock + save/load. The spent-not-elapsed day counter; IndexedDB persistence storing seeds + deltas; a stamped schema version for future migrations.
  6. Dev harness. A bare inspector page — generate and dump runners and sites, roll the day, save and reload — to verify the models produce sane, varied, reproducible output before any game UI exists.
Phase 0 done = we can conjure a believable runner market and a believable job site from seeds, watch them vary and persist, and trust the data before building a single screen on top of it.

07

Deferred Polish Backlog

Work that's explicitly not a current-pass blocker — flagged here so it doesn't get lost. Items marked resolved were settled in design and now live in the Phase 2 work plan; they still need implementing.

  • Flavor text volume. Personality lines and aims lines currently ship as small placeholder pools (§09's identity fields) — enough to prove the generator wires them in, not enough for real market variety at scale. Come back and expand both pools substantially once the systems around them are proven.
  • resolvedHandle/name formatting. Expanded into genuine formatting variety — larger pools, L337 spellings, and anti-collision so two near-identical handles can't surface in one universe.
  • Obstacle placement tuning (site generator). Room post-slot counts by size (small/medium/large → 1/2/3) and patrol/zone route count per site (0-2) are provisional defaults, not derived from anything. More importantly: transition points (edges) currently place obstacles evenly/round-robin regardless of distance from the objective room. Revisit so that transitions closer to the objective can roll concentrated, layered security — the classic image of a maglock door, a camera, a hardpoint turret, and an armored guard all standing between the crew and the payload at once, rather than one obstacle type spread thin across the whole route. A "closer to the objective, more likely to stack" weighting is the piece still missing.
  • Immunities need a scannable in-fiction tell. Every Watsonian immunity an obstacle instance can roll (sensor-equipped, hardened against tampering, air-gapped, cloaked against astral perception — currently just a reason string on the affected affordance) needs a corresponding observable artifact a player can actually notice: a visible sensor rig, telltale shielding, a spirit's aura reading as unusually old or bound. Same "recon is a sensor, not a dial" principle the job-board scouting system already runs on (§06), applied to per-obstacle immunities. The data already carries everything needed — what's missing is the scan/observe interaction and the UI for revealing it.
  • resolvedMetatype and Awakened distribution. Settled: Human 50 / Ork 20 / Elf 10 / Dwarf 10 / Troll 10, with the Awakened a full third of the market (~25% mages, ~8% adepts). Above the Sixth World's ~1% baseline because a runner market is self-selected; well below an even split because humans must read as the default. Two dials produce it and must move together — the metatype draw and the focus draw, since mage focuses are Awakened by construction and their share of the focus table sets a floor. Implementation pending.
  • resolvedTask resolution needs an attribute in the dice pool. Settled: pool becomes Skill + Attribute, with a full mapping across seven attributes (Strength restored; Body and Willpower carry no skills and are the pure soak stats). This is now P2.0 and blocks the rest of Phase 2 — evasion is Agility and Initiative is Agility + Intelligence, so combat cannot exist without it.
  • resolvedKarma growth needs to consider Attributes. Settled: a reserved share of every award banks into an attribute fund, spent on the focus's key attribute first, then attributes backing archetype skills; skills keep the existing cascade with the remainder. Tabletop attribute pricing is explicitly not used — that cost assumes a player choosing to save up, whereas an automatic cascade buys the cheapest affordable thing and would never reach an attribute at all. Metatype now sets attribute ceilings rather than starting deltas.
  • Reputation's actual scaling and impact needs defining. Currently a flat +1 per completed job — a bare placeholder proving the field exists and gets touched. It's meant to represent negotiating power as a Johnson (access to and discounts on purchasable things), but neither how much a job should be worth in Reputation (flat? scaled by pay/tier/mission count?) nor what Reputation unlocks has been designed. Needs real attention once there's an armory/purchase system for it to modify.
  • Job/mission sequencing is still a placeholder shape. A job correctly bundles 1+ missions, but missionCount is a flat uniform roll (1-3) with no distribution behind it, and there's no player-facing concept yet of running extra, non-contracted prep missions (recon, softening a target) before committing the closing mission — real designed-for gameplay (Karma to every runner involved, nuyen only once) that now has a dispatch system to hang off. Route-type missions (movement between two sites — the Gauntlet transit case) are a reserved shape (locationType) that site.js still can't generate.
  • Ammunition. Burst and full auto burn rounds; without tracking them, fire modes are free upside and a firefight has nothing to run out of. Planned for late in Phase 2, alongside the rest of the depletion layer.
Why deferred, not dropped: none of this blocks any system from being provably fun in simulation mode — a placeholder pool exercises the generator exactly as well as a large one. Expanding it is pure content volume, cheapest to do in a dedicated pass rather than piecemeal while the mechanical foundation is still moving.
